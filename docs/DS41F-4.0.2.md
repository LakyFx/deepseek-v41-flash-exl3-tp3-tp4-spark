# TensorFold TP4 4.0.2 - exact production recipe

4.0.2 is the public name for the qualified **4.0.1a combined A** payload.
The measured binaries, target weight values and sampling behavior are unchanged
by publication. It retains the smart KV cache controller and Smart Adaptive
speculation. [Benchmark tables and definitions](BENCHMARK-4.0.2.md).

| Setting | Value |
| --- | --- |
| Model | DeepSeek-V4.1-Flash-1017, LakyFx mixed EXL3 ~3.51 bpw routed experts |
| Topology | Four DGX Sparks, switchless cycle, target TP4 |
| Capacity | C16, adaptive shared R48, at most five draft tokens |
| KV / head checkpoints | 9,000,000 positions / 3.5 GiB |
| Compute / physical KV quantum | 8192 / 2048 tokens |
| Context | 401408 tokens |
| Relocation credit | Existing 320 MiB per rank, refill 8 MiB/s |
| Source | `v402`, full content-addressed source recipe |
| Native weight layout | `balanced401a-v1`; all four ranks must match |
| Vision | Two in flight; MAX, 8192 reasoning + 32768 final headroom |

## What changed since 4.0.0

- **Less decode work:** H2 performs exact greedy result reduction before
  transport. D1 omits an unused final draft vocabulary projection. M1 skips
  eligible empty MoE work without changing target arithmetic.
- **Better use of measured costs:** K1 starts the existing speculative allocator
  with measured TP4 cost priors; online calibration continues. R48 is a shared
  maximum, not 48 drafts per stream. This does not train the model weights.
- **Distributed draft work:** S1r6 places independent DSpark sessions on two
  TP2 pairs. The target model still runs TP4; this is not two target replicas.
- **Balanced weight payload:** alternate whole 128-column gate/up blocks over
  20 of 40 target layers. Approximately 66.18/58.00 GiB becomes 62.12/62.06 GiB
  per rank. No requantization; down, attention, head, draft and Engram splits
  remain unchanged. Total runtime RAM also includes buffers and host services.
- **Bounded checkpoint work:** batch release of 2-16 already-dead checkpoints;
  a weak first-continuation tie-break within the existing placement budget.
  It cannot introduce new proven-reuse victims or new GPU moves; the 2ms CPU
  deadline remains. Existing long-context protection is retained.
- **Vision recovery:** duplicates join a durable logical job. At most one
  repair attempt follows confirmed termination of the previous dispatch;
  unknown backend state never authorizes overlapping retries. Attempts share
  the original finite job deadline. Ordinary agent histories keep their route.

These features are not isolated speedup claims. See the exact measured scope.

## 1. Preserve topology, source weights and old installations

Follow the [4.0.0 host/topology/NCCL instructions](DS41F-4.0.0.md#1-prepare-the-host-and-switchless-transport)
on the same four-rank cycle. Use the separately patched pinned NCCL library;
do not substitute an unpatched system library. The credited topology patches,
base kit, model metadata, tokenizer/template and two-way owned Engram files
are unchanged. Do not run the 4.0.0 head/follower binaries with new caches.

```sh
git clone https://github.com/LakyFx/deepseek-v41-flash-exl3-tp3-tp4-spark.git
cd deepseek-v41-flash-exl3-tp3-tp4-spark
git checkout v4.0.2
python3 tensorfold/extract.py --out /srv/ds41f-source-4.0.2
python3 -m tensorfold.tp4.v402.build \
  --kit /srv/ds41f-source-4.0.2/kit --out /srv/ds41f-tp4-4.0.2
```

The staging command verifies the exact measured five Linux ARM64 executables,
two additional CUDA kernels and existing isolated TP4 AOT assets before writing
a new output. No service, network configuration or running model is changed.
Use the documented 4.0.0 preparation tools for the unchanged `model/`, `kit/`
and `engram-tp2-r{0,1}/` inputs. Give every rank its own runtime root.

For an optional source rebuild, extract a NEW base and materialize `v402`:

```sh
python3 -m tensorfold.variants.build build --recipe v402 \
  --build-root /srv/ds41f-source-4.0.2 --out /srv/ds41f-rebuilt-4.0.2
```

This compiles from the exact source with the existing pinned Zig/toolchain and
base fatbins. Rebuilt bytes can differ; qualify them separately. The default
4.0.2 staging path uses the supplied measured executables. CUDA source/build
scripts for the additional kernels are in `tensorfold/tp4/v402/cuda/`; compiler
commands are CPU-only when `CUDA_VISIBLE_DEVICES` is empty. Rebuilt kernels
also require destination qualification and updated receipts.

## 2. Produce balanced caches offline, preserving original files

First obtain the original native TP4 caches using the preserved
[TP3-to-TP4 byte repartition procedure](DS41F-4.0.0.md).
An existing 4.0.0 installation can reuse its original caches as inputs.
For output rank N the second input is its column partner **N XOR 2**:
0+2, 1+3, 2+0, 3+1. It must be the original layout, not already balanced.

Decompress the selected public native key plan:

```sh
gzip -dc tensorfold/tp4/v402/plan/rank0.keys.gz > /srv/rank0-balanced.keys
```

Read the actual original index digests, then export each rank to a NEW directory
with its actual source/partner paths and digests:

```sh
python3 -m tensorfold.tp4.v402.repack_weights \
  --source /srv/original/rank0of4.bin --partner /srv/original/rank2of4.bin \
  --rank 0 --source-index-sha256 REPLACE_SOURCE_INDEX_SHA256 \
  --partner-index-sha256 REPLACE_PARTNER_INDEX_SHA256 \
  --output /srv/ds41f-tp4-4.0.2/rank-cache/rank0of4-balanced401a-v1-local.bin \
  --native-keys /srv/rank0-balanced.keys --write --verify-writes
```

Default without `--write` is plan-only. The exporter preserves every EXL3
trellis/sign byte, verifies every written tensor by rereading it, and produces
a receipt. New output is roughly 250 GiB across all ranks; arrange sufficient
disk space and transport the required inputs. Its `.partial` is a hardlink to
the finished file, not a second payload. Keep previous weights for rollback.

Independently compare every output byte against overlapping original columns:

```sh
python3 -m tensorfold.tp4.v402.verify_export \
  --output /srv/ds41f-tp4-4.0.2/rank-cache/rank0of4-balanced401a-v1-local.bin \
  --source /srv/original/rank0of4.bin --partner /srv/original/rank2of4.bin
python3 -m tensorfold.tp4.v402.cache \
  --directory /srv/ds41f-tp4-4.0.2/rank-cache --rank 0 --deep
```

Repeat for ranks 1-3 with matching key plans. On each node, keep exactly one
`rankNof4-*.bin` in its new runtime cache directory with the receipt beside it.
The exporter rejects overwriting old inputs. Never infer GPU readiness from a
successful file copy alone. The published native protocol rejects mixed ranks.

## 3. Configure, verify and launch the four ranks together

Copy `tensorfold/tp4/cluster.example.json` to private operator configuration.
Replace documentation addresses, NIC/GID names, paths and the NCCL library path
with the verified four-node topology. Point each rank's `root` at its NEW
4.0.2 runtime. Do not commit that operator configuration.

```sh
# Print only; does not start the engine:
python3 -m tensorfold.tp4.v402.launch --config /srv/cluster.local.json --rank 0
# During your chosen maintenance window, on each corresponding node:
python3 -m tensorfold.tp4.v402.launch --config /srv/cluster.local.json --rank 0 --run
```

Use ranks 0,1,2,3 on their matching nodes. `--run` verifies source/binary/kernel
receipts, balanced cache index/native keys, metadata/template, Engram and NCCL.
It validates the cache index at every start; full ~62GiB rehashing is the explicit
offline `--deep` operation. Preserve the existing all-four-node recovery barrier
and operator-owned API configuration. This publication does not install or
restart an OS service. All ranks must be healthy before admitting traffic.

## 4. Optional serving gateway

Install the updated [gateway package](GATEWAY.md) and select
`tensorfold/tp4/v402/gateway-profile.json` plus the matching
`gateway.env.example`. Required public settings include
`DGX_VISION_CONTROL_ENABLED=1` and `DGX_VISION_RECOVERY_ATTEMPTS=2`.
Supply your own API key, TLS and private state location; existing client URLs
and credentials need not change. The ledger migration is additive: preserve
operator state and rehearse an existing DB migration on a copy first.
For a later downgrade, the inspect-only `gateway/rollback_402.py` checks queued
repair compatibility; `--apply` is for a stopped gateway only and refuses
unreconciled running/unknown attempts. Successful job results are preserved.

Standalone vision uses MAX/8K reasoning, 32K final headroom, two concurrent jobs,
finite queue/job deadlines and cancellation receipts. A transport disconnect
alone does not prove a GPU job stopped. Unknown attempts keep their physical
slot until reconciliation; success is reused for duplicate submissions.
