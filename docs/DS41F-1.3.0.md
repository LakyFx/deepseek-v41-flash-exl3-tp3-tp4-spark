# TP3 1.3.0 — image-aware cache and validated JSON

This is the current three-Spark recipe. It combines the GPU-qualified native
1.2.9 port with the production 1.3.0 gateway. TP4 remains independently versioned
as 4.0.4; publishing this release does not update an existing TP4 installation.

## What changed since published TP3 1.2.8

| Component | Behavior |
|---|---|
| Smart CUDA Graph Controller | Bounds graph retention using measured reuse/cost and memory headroom; coordinates safe retirement across ranks. |
| Current B kernels | Guarded EXL3 mid-M dispatch from the qualified TP4 4.0.4-B work, adapted and numerically checked for TP3. Original fallbacks stay active. |
| Long histories | Alias-safe amortized template accumulation reduces repeated CPU copying; prompt/token parity checked. |
| Image-bearing prefix cache | Cache-only image identities include prepared content and span geometry; unchanged image history can resume. A changed image invalidates reuse beyond its span. Fully restored image spans skip their tower/rows. |
| Reported fatal CUDA errors | A reported fatal context fault causes the affected process to exit for coordinated generation recovery. This is not a silent-hang detector. |
| Explicit JSON | Chat `response_format`, Responses `text.format`, and `guided_json` receive strict output validation and at most one bounded correction. Ordinary traffic bypasses it. |

The image-cache contribution is from **hteak**, supplied in
[issue #2](https://github.com/LakyFx/deepseek-v41-flash-exl3-tp3-tp4-spark/issues/2).
Their original patch is preserved with its digest and attribution in
[IMAGE-CACHE-CREDITS.txt](../tensorfold/tp3/v130/IMAGE-CACHE-CREDITS.txt).
LakyFx added integration, namespace/OOM/multiple-image regressions and independent
TP3 GPU validation. Related prior work: Thomas Kempka / thkempka and Mauvis
Ledford / krunkosaurus, as detailed in that credit file. Kernel and engine source
retain their existing TensorFold/ExLlama licenses and upstream attribution.

## Preserved production envelope

Three ranks, original direct-peer TP3 triangle; DeepSeek V4.1 Flash 1017 EXL3
3.5 bpw, identical published model shards, **C12**, adaptive **R48 ceiling**,
**7M physical KV**, **3 GiB checkpoints**, **320 MiB relocation credit**, 401,408
context, **4K logical prefill / 2K physical quantum**. All three smart controllers
and the activity-limited NVMe companion are retained. Each weight rank has
85,892,651,432 bytes. No new quantization or sampling defaults.

Both standalone and inline agent-history vision preserve MAX reasoning,
8,192 reasoning tokens, 32,768 final-answer headroom and C2 image concurrency,
with the existing durable queue, cancellation and recovery protocol.

## Installation and source

Use the existing [TP3 weight/network preparation](TENSORFOLD-INSTALL.md) and
[1.2.8 head template](DS41F-1.2.8.md); the head template and model metadata are
unchanged. Supply your own addresses, paths, credentials and topology in
`tensorfold/cluster.local.json`, based on `tensorfold/cluster.example.json`.
Do not launch on the four-Spark ring using the TP3 example masks.

The exact 1.2.9 native source is published under both `v129` and `v130` selectors;
1.3.0 changes the gateway only. Objects, complete source manifests and the
prebuilt ARM64 payload are SHA256-bound. To reconstruct source, extract the
preserved `tensorfold/artifacts/tensorfold-source.tar.gz` into a fresh directory
then call `tensorfold.variants.patch.apply(source, 'v130')`. The original
`.zig-version`, build inputs and source headers are retained. A rebuilt binary
needs local qualification; the packaged binaries are the actually qualified ones.

Stage into a new directory, then install additively into an existing prepared TP3
runtime containing the base `kit`, verified model/rank caches and Engram:

```sh
python3 -m tensorfold.tp3.v130.build stage --out runtime-130-staged
python3 -m tensorfold.tp3.v130.build install --staged runtime-130-staged --runtime /your/tp3-runtime
python3 -m tensorfold.tp3.v130.launch --config tensorfold/cluster.local.json --rank 0
```

Print/inspect every rank command before adding `--run`. Run rank 0, 1 and 2 on
their respective machines. The installer never starts/stops a service, replaces
an existing version or changes network configuration. All three ranks must use
the same release. A TP4 shell's controlled variables are cleared by the launcher.
Retain the base kit: the new version uses read-only references plus its own
verified B-kernel overlay. Install the existing NVMe companion on each rank.

For serving, install `./gateway` into an independent venv, preserving your
existing dependency freeze, credentials and durable job database. Use
`DS41F_GATEWAY_PROFILE` with
`tensorfold/tp3/v130/gateway-profile.json`; see the accompanying
`gateway.env.example` and [gateway guide](GATEWAY.md). The default package policy
now targets TP3 1.3.0; **TP4 users must explicitly select their own TP4 profile**.
The five added CPU dependencies are pinned in `gateway/pyproject.toml`.

## JSON guarantees and limits

Only explicit JSON contracts are adapted. The gateway preserves the original
history prefix and adds a late, budgeted format instruction. It validates full
JSON syntax and supported JSON Schema, including local references, in a bounded,
killable CPU worker. No external schema resources are fetched. Successful final
answers satisfy the accepted contract; unsupported schemas or unresolved failures
return explicit errors. At most one correction uses the remaining original token
budget and real usage is aggregated. Tool intermediates and refusals retain
their protocol; provider errors are not blindly regenerated.

JSON SSE is validated before the final content is released, with heartbeats
while waiting. Durable image jobs are validated before successful persistence.
This is **gateway validation and bounded repair, not native constrained decoding**.
It cannot guarantee every unconstrained generation succeeds or that JSON values
are factually correct. CPU validation and a possible repair add request latency;
they do not change GPU kernels or ordinary decode policy.

## Validation and measurements

- **199/199** Linux gateway regressions and **11/11** live API checks, including
  Chat/Responses image JSON, SSE, local schema references and tool intermediates.
  Successful live cases required **zero corrections**.
- Image reuse: **6/6** single-image and **4/4** multi-image checks. A second-image
  change kept 11,374 valid earlier tokens and recomputed 1,753; unchanged history
  reused 12,998 and computed 164 new tokens.
- Inherited native 1.2.9 heavy workflow: **77/78**, 1,322.27 seconds, 45 tool
  correction events; 35 recovered and one C12 replica hit the 16-turn guard.
  This heavy benchmark was not rerun for the gateway-only 1.3.0 update.
- Native 1.3.0 sanity screen: C1/C6/C12 code medians **104.15/32.94/20.52 tok/s**,
  prose **80.01/29.79/18.25 tok/s per request**; greedy, thinking off, 512 output
  tokens. It calls the native engine directly, bypassing JSON adaptation.
- Zero-hit cold prefill: **3,479 tok/s at 32K**, **3,537 tok/s at 64K**.

These are one-pass screening results, not SparkDash/RigMark or statistical paired
A/B data. Old C12 baseline passes themselves differed by roughly 4%; do not
present small changes as proven speed gains or regressions. Preserved historical
benchmarks retain their original labels. [Numeric evidence](../results/20261104-1.3.0/QUALIFICATION.json).

Vision cache correctness does not guarantee visual perception: a deliberately
contradictory old visual history produced the wrong label even on a true cold
run. Emergency swap remains enabled; late cold-page reclaim was observed in
the native baseline and is not claimed fixed by JSON compatibility. No reboot
drill was performed. Keep your prior version and operator-owned state for rollback.

No new flyer is included in this release.
